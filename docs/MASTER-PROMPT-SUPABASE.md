Ниже приведён самодостаточный промпт для разработки полнофункционального веб-сервиса квартального ревью команд. Его можно передать Codex, Claude Code или другой системе разработки. # МАСТЕР-ПРОМПТ ДЛЯ РАЗРАБОТКИ

Ты — ведущий full-stack-разработчик и архитектор. Разработай работающий сервис **MOEX QBR Tool** — систему квартального ревью продуктовых команд компании.

Не ограничивайся статичным макетом. Нужен полноценный сервис с фронтендом, базой данных, аутентификацией, серверной логикой, сохранением пользовательских изменений и развёртыванием. Приложение должно воспроизводить продуктовую концепцию существующего прототипа, но использовать согласованную нормализованную модель данных и реальные CRUD-операции.

Если какая-либо деталь не определена, принимай минимальное и логичное решение, соответствующее этому документу. Не добавляй функции, не связанные с квартальным ревью. Не заменяй работающую функциональность декоративными заглушками, кроме явно обозначенных будущих интеграций.

## 2. Продуктовая задача

### 2.1. Проблема

Квартальное ревью продуктовой команды часто готовится вручную из разрозненных таблиц, презентаций и статусов. Метрики, инициативы, риски и решения существуют отдельно, поэтому руководителю сложно быстро понять:

1. Какие стратегические цели поддерживает команда.
2. Какие результаты планировались и какие фактически достигнуты.
3. Какие инициативы повлияли на результат.
4. Где находятся риски и ограничения.
5. Какие управленческие решения нужно принять.

### 2.2. Продуктовая гипотеза

Если связать стратегию компании, цели, метрики, инициативы, ресурсы, риски и решения в единой структуре, а затем автоматически сформировать управленческое резюме, подготовка QBR станет быстрее, а сама встреча будет сфокусирована на отклонениях и принятии решений.

### 2.3. Основная иерархия

Сервис обязан поддерживать сквозную структуру:

**Стратегическое направление → Стратегическая цель → Метрика → Инициатива → Результат периода → Вопрос → Решение**

Дополнительные связи:

- инициатива относится ровно к одной стратегической цели;
- инициатива связана с одной или несколькими метриками этой цели;
- инициатива принадлежит команде и имеет владельца;
- ресурс инициативы складывается из FTE назначенных сотрудников;
- риск относится к инициативе в конкретном QBR-периоде;
- вопрос относится к конкретному QBR-периоду;
- решение может относиться к вопросу либо быть самостоятельным;
- значения метрик и прогресс инициатив фиксируются отдельно для каждого квартала.

## 4. Пользователи и права доступа

### 4.1. Тестовая учётная запись

- Логин: `moex_test`
- Пароль: `moex_test`

Supabase Auth использует email/password. На экране пользователь вводит логин `moex_test`, а клиентское приложение преобразует его в технический email `moex_test@qbr.local`. Пароль нельзя хранить или проверять в клиентском коде. Тестовый пользователь создаётся серверным seed-скриптом через Supabase Admin API.

### 4.2. Первая версия прав

Все данные доступны только аутентифицированному тестовому пользователю. Анонимный пользователь видит только страницу входа. Все таблицы должны быть защищены Row Level Security.

Архитектура должна допускать добавление организаций и нескольких пользователей в следующих версиях. Поэтому основные бизнес-сущности содержат `organization_id`, даже если в seed используется одна организация.

## 7. Расчёты и бизнес-правила

### 7.1. Нормализация чисел

Функция расчёта должна извлекать число из значений:

- `52,4 тыс.` → `52.4`;
- `18%` → `18`;
- `9 дней` → `9`;
- `4 продукта` → `4`.

План и факт одной метрики должны использовать одинаковую единицу измерения. Для расчёта отношения множитель единицы сокращается. В UI сохранять исходную строку с единицей измерения, а в базе дополнительно хранить числовое нормализованное значение.

### 7.2. Выполнение метрики

Для метрики «больше — лучше»:

`progress = round(actual_numeric / target_numeric × 100)`

Для метрики «меньше — лучше»:

`progress = round(target_numeric / actual_numeric × 100)`

Примеры:

- `52,4 / 50 = 104,8%` → `105%`;
- `16,3 / 18 = 90,6%` → `91%`;
- для времени запуска `7 / 9 = 77,8%` → `78%`;
- `4 / 4 = 100%`.

Сохранять реальное значение progress без верхнего ограничения. В progress bar визуально ограничивать значение 100%, но рядом показывать фактические 105%.

Если значение не распознано, равно null либо делитель равен нулю, progress равен null, а UI показывает «Недостаточно данных». Не подменять ошибку нулевым результатом.

### 7.3. Статус метрики

- зелёный: progress ≥ 100%;
- жёлтый: 85–99%;
- красный: progress < 85%;
- серый: progress отсутствует.

Статус рассчитывается сервером и не редактируется вручную.

### 7.4. Прогресс инициативы

Квартальный прогресс инициативы рассчитывается по её собственному плану и факту, а не по значению связанной метрики. Формула для первой версии: `fact / plan × 100`.

Например, у инициативы может быть план `20 витрин`, факт `11 витрин`, прогресс `55%`, а связанная метрика «Время запуска эксперимента» имеет отдельный план `7 дней`, факт `9 дней`, выполнение `78%`.

Статус инициативы является статусом жизненного цикла и не обязан автоматически совпадать с прогрессом. Завершённая инициатива может не достичь целевого эффекта; это допустимо и должно быть видно в итогах.

### 7.5. FTE

FTE инициативы равен сумме `allocation_fte` активных назначений сотрудников в конкретном QBR-периоде.

- один сотрудник по умолчанию даёт `1.0 FTE`;
- разрешены дробные значения от `0.1` до `1.0` на сотрудника;
- один сотрудник может участвовать в нескольких инициативах;
- общий FTE инициативы не хранить как независимый источник истины; вычислять суммой либо поддерживать серверным триггером/представлением.

### 7.6. Риски

Уровни:

- low — низкий;
- medium — средний;
- high — высокий.

В таблицах показывать общее число рисков. В tooltip показывать количество каждого уровня. В итогах учитывать только активные риски периода.

### 7.7. Готовность к ревью

Использовать семь равновесных критериев:

1. В QBR есть хотя бы одна инициатива.
2. В QBR есть хотя бы одна метрика.
3. У всех метрик заполнены корректные план и факт.
4. У всех инициатив есть связанные метрики, присутствующие в QBR.
5. У всех инициатив заполнены владелец, команда и FTE больше нуля.
6. Добавлен хотя бы один вопрос.
7. Нет инициатив в статусе «Пауза».

`readiness = round(количество выполненных критериев / 7 × 100)`

Показывать невыполненные критерии рядом с оценкой. Значение пересчитывается на сервере после каждого изменения данных периода.

### 7.8. Оценка связности

Начальное значение — 100%. Вычитать:

- 12 п.п. за каждую метрику без связанной инициативы;
- 10 п.п. за каждую инициативу без метрики;
- 6 п.п. за каждую метрику с ручным источником.

Ограничить диапазон 0–100%. Показывать конкретные несвязанные сущности, а не только процент.

### 7.9. Влияние на стратегические цели

Для первой версии рассчитывать как среднее выполнение метрик QBR, ограничивая вклад каждой метрики значением 100%:

`impact = round(sum(min(metric.progress, 100)) / number_of_metrics)`

Отдельно показывать число уникальных стратегических целей, поддержанных инициативами, и метрику с минимальным выполнением.

## 8. AI-анализ

### 8.1. Архитектура

AI-запрос выполняется только через Supabase Edge Function. API-ключ провайдера хранится в Supabase Secrets. Клиент не должен видеть ключ.

Рекомендуемый провайдер — OpenRouter. Модель задаётся переменной окружения `AI_MODEL`. Реализовать таймаут, обработку ошибок и повтор не более одного раза.

### 8.2. Входные данные

Передавать только данные выбранного QBR-периода:

- команда и квартал;
- цели;
- метрики с планом, фактом и процентом;
- инициативы с прогрессом, FTE и рисками;
- вопросы и решения;
- готовность, связность и влияние.

Не передавать email сотрудников и другие ненужные персональные данные.

### 8.3. Требования к AI

AI должен:

- использовать только переданные факты;
- не придумывать достижения, причины и зависимости;
- явно отмечать недостаток данных;
- показывать отклонения цифрами;
- отделять результат от предположения;
- выдавать структурированный JSON.

Формат ответа:

```json
{
  "headline": "Краткий управленческий вывод",
  "summary": "Резюме периода в 3–5 предложениях",
  "achievements": ["..."],
  "attention_points": ["..."],
  "risks": ["..."],
  "data_quality_issues": ["..."],
  "discussion_questions": ["..."],
  "recommended_actions": ["..."]
}
```

Валидировать результат через Zod. Если JSON невалиден, показать понятную ошибку и не затирать предыдущий успешный анализ.

### 8.4. Хранение результата

Сохранять:

- тип анализа;
- входной snapshot hash;
- модель;
- JSON-результат;
- дату;
- пользователя.

Если данные периода изменились после анализа, показывать метку «AI-обзор требует обновления».

1. Собрать React-приложение командой `npm run build`.
2. Загрузить содержимое `dist` в публичный Storage bucket `web`.
3. Установить в Vite `base: './'` и использовать `HashRouter`, поэтому все клиентские маршруты открываются через один `index.html` и не требуют server-side history fallback.
4. Развернуть публичную Edge Function `web` с `verify_jwt = false`. Она отдаёт `index.html` и проксирует статические assets из bucket `web` с корректными `Content-Type`, cache headers и CORS. Публичен только application shell; бизнес-данные по-прежнему защищены Supabase Auth и RLS.
5. Внешней ссылкой является URL Edge Function с завершающим `/`, например `.../functions/v1/web/`, чтобы относительные пути assets разрешались внутри маршрута функции.
6. Добавить скрипт `npm run deploy:supabase`, который собирает SPA, синхронизирует bucket и развёртывает функции.

Если в используемом тарифе доступен официальный Supabase Hosting, разрешается заменить Storage + Edge Function на него, не меняя остальную архитектуру.

## 11. Серверные операции

Критичные изменения выполнять через PostgreSQL Functions/RPC или Edge Functions в транзакции.

### 11.1. `add_initiative_to_qbr(period_id, initiative_id)`

Операция должна:

1. Проверить доступ пользователя к QBR.
2. Проверить статус периода `preparation`.
3. Проверить, что инициатива ещё не включена в другой QBR того же года и квартала.
4. Создать `qbr_initiatives`.
5. Скопировать владельца, команду и состав инициативы из `initiative_members`.
6. Добавить связанные метрики в `qbr_metrics`, если их ещё нет.
7. Создать `qbr_metric_initiatives`.
8. Пересчитать готовность, связность и влияние.

### 11.2. `remove_initiative_from_qbr(period_id, qbr_initiative_id)`

Операция должна:

1. Удалить инициативу периода, состав и риски.
2. Удалить связи с метриками.
3. Удалить из QBR только те метрики, которые больше не связаны ни с одной инициативой.
4. Пересчитать оценки периода.

### 11.3. `update_qbr_metric_values(qbr_metric_id, target, actual, source)`

Операция должна:

- проверить статус `preparation`;
- нормализовать значения;
- проверить совместимость единиц;
- пересчитать progress и status;
- обновить `updated_at`;
- пересчитать оценки периода;
- пометить AI-анализ устаревшим через изменение input hash.

### 11.4. `transition_qbr_status(period_id, target_status)`

Разрешённые переходы:

- preparation → review;
- review → preparation;
- review → results.

Условия:

- preparation → review: readiness ≥ 70;
- review → results: у каждого вопроса есть решение;
- results является закрытым состоянием в первой версии;
- изменение данных целей, метрик, инициатив, FTE, рисков и вопросов разрешено только в preparation;
- изменение решений разрешено только в review;
- results доступен только для чтения.

Проверки должны находиться на сервере, а не только в интерфейсе.

### 11.5. `create_future_qbr_period(qbr_id, year, quarter)`

Создаёт пустой период в preparation. Не копирует данные автоматически. Инициативы, метрики и вопросы добавляются пользователем.

## 12. Row Level Security

Включить RLS на всех бизнес-таблицах.

Основной принцип:

- пользователь читает данные организации из своего `profiles.organization_id`;
- пользователь видит QBR только при наличии записи в `qbr_access`;
- owner/editor может изменять QBR;
- viewer только читает;
- анонимный пользователь не имеет доступа;
- операции изменения статуса и составных сущностей выполняются через security definer functions с обязательной проверкой пользователя и роли;
- service role используется только в seed и Edge Functions, никогда в браузере.

Добавить SQL-тесты, подтверждающие невозможность чтения и записи без сессии.

## 15. Пользовательские сценарии

### UC-01. Вход

1. Пользователь открывает приложение.
2. Без сессии видит страницу входа.
3. Вводит `moex_test` / `moex_test`.
4. Система выполняет вход через Supabase Auth.
5. Открывается «Мои QBR».
6. После обновления страницы сессия сохраняется.

### UC-02. Выход

1. Пользователь нажимает «Выйти».
2. Сессия Supabase завершается.
3. Защищённые данные очищаются из кеша.
4. Открывается страница входа.

### UC-03. Просмотр стратегии

1. Пользователь открывает «Стратегия».
2. Видит направления, цели, метрики и агрегированную информацию по инициативам.
3. Нажимает «Открыть инициативы» и переходит в портфель с применённым фильтром по цели.

### UC-04. Добавление метрики

1. Пользователь открывает «Метрики».
2. Нажимает «Добавить метрику».
3. Выбирает цель и заполняет название, описание, категорию, направление и ручное значение.
4. Система проверяет обязательные поля и уникальность названия.
5. Метрика появляется в таблице и становится доступна для инициатив выбранной цели.

### UC-05. Редактирование и переименование метрики

1. Пользователь открывает форму редактирования.
2. Меняет название или другие атрибуты.
3. Сервер обновляет справочник.
4. Связи хранятся по UUID и не разрываются.
5. Исторические snapshots QBR сохраняют старое название, текущий незакрытый период может получить новое название по отдельной синхронизации.

### UC-06. Создание команды и сотрудника

1. Пользователь создаёт команду.
2. Раскрывает строку.
3. Добавляет сотрудника.
4. Система проверяет уникальность email.
5. Сотрудник становится доступен для выбора владельцем и участником инициативы.

### UC-07. Добавление инициативы в портфель

1. Пользователь нажимает «Добавить инициативу».
2. Выбирает стратегическую цель.
3. Система показывает только метрики этой цели.
4. Пользователь выбирает одну или несколько метрик, команду и владельца.
5. FTE предзаполняется доступным FTE команды.
6. Пользователь при необходимости корректирует распределение.
7. Инициатива сохраняется и появляется в таблице.

### UC-08. Подготовка QBR

1. Пользователь выбирает QBR и текущий квартал.
2. В статусе preparation добавляет инициативу из портфеля.
3. Система автоматически добавляет связанные метрики.
4. Пользователь вводит квартальный план и факт инициативы.
5. Пользователь вводит целевые и фактические значения метрик.
6. Проценты и статусы пересчитываются автоматически.
7. Пользователь корректирует команду, состав и FTE.
8. Добавляет риски.
9. Добавляет вопросы к ревью.
10. Готовность пересчитывается и показывает невыполненные критерии.

### UC-09. Удаление инициативы из QBR

1. Пользователь удаляет инициативу периода.
2. Система удаляет назначения и риски этой инициативы периода.
3. Метрика остаётся, если связана с другой инициативой QBR.
4. Неиспользуемая метрика удаляется из QBR.
5. Готовность и оценки пересчитываются.

### UC-10. Начало ревью

1. При готовности ≥70% пользователь нажимает «Начать ревью».
2. Сервер проверяет готовность и меняет status на review.
3. Основные данные становятся read-only.
4. Появляется AI-обзор и формы решений.

### UC-11. Проведение ревью

1. Пользователь просматривает результаты, риски и AI-выводы.
2. По каждому вопросу вводит решение.
3. При необходимости добавляет самостоятельное решение.
4. Счётчик `N/M` обновляется.
5. Пока решения есть не у всех вопросов, завершение ревью заблокировано.

### UC-12. Завершение ревью

1. Пользователь нажимает «Завершить ревью».
2. Сервер повторно проверяет решения.
3. Период переходит в results и блокируется для редактирования.
4. Формируется или обновляется AI-резюме.
5. Открывается экран итогов.

### UC-13. Итоговый отчёт

1. Пользователь видит AI-резюме, KPI, цели, метрики, вложенные инициативы и решения.
2. Решения к вопросам показывают вопрос и решение.
3. Самостоятельные решения не показывают фиктивный вопрос.
4. Пользователь нажимает PDF и сохраняет печатную версию.

### UC-14. Переключение квартала

1. Пользователь нажимает стрелку назад.
2. Прошлый QBR открывается в results.
3. Пользователь нажимает стрелку вперёд.
4. Текущий период возвращается с сохранёнными данными и статусом.
5. При переходе в новый будущий квартал создаётся пустой preparation.

### UC-15. Обновление AI-анализа

1. Пользователь в review нажимает «Обновить AI-обзор».
2. UI показывает загрузку и блокирует повторный запрос.
3. Edge Function формирует snapshot, вызывает OpenRouter и валидирует JSON.
4. Новый результат сохраняется.
5. При ошибке предыдущий результат остаётся доступен.

## 18. Обработка ошибок

- показывать toast после успешного сохранения;
- показывать inline-ошибки формы;
- не использовать `alert()`;
- сохранять введённые данные формы при временной ошибке сети;
- блокировать повторное нажатие во время мутации;
- использовать optimistic update только для безопасных простых действий;
- для составных операций ждать подтверждения сервера;
- пустые или невалидные числовые значения не считать нулём;
- при конфликте статуса обновить данные и объяснить, что QBR уже изменён;
- AI-ошибка не должна блокировать ручной сценарий ревью.

# Главные решения модели данных

1. Справочники отделены от квартальных snapshots.
2. История QBR не изменяется при редактировании метрики или инициативы в справочнике.
3. Метрики попадают в QBR только через инициативы.
4. FTE считается из назначений сотрудников.
5. Риски относятся к инициативе конкретного периода.
6. Решение имеет nullable-связь с вопросом; фиктивные вопросы не используются.
7. Проценты и переходы статуса проверяются сервером.
8. AI-результат версионируется по hash входных данных.
